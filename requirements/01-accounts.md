# 01 บัญชีและการตรวจสอบคุณสมบัติ

## AUTH — เข้าสู่ระบบและบัญชี

| รหัส | Requirement | สถานะ |
|---|---|---|
| AUTH-01 | ระบบต้องมีหน้า login ของ admin โดยกรอก username และ password | ✅ |
| AUTH-02 | ระบบต้องมีหน้า login ของผู้ใช้ โดยกรอก username และ password แยกจากหน้า admin | ✅ |
| AUTH-03 | ระบบต้องมีหน้า register ของผู้ใช้ โดยกรอก fullname, username, password, **ยืนยัน password**, email | ✅ (4 ช่องหลัก) / ⚠️ (ช่องยืนยัน) |
| AUTH-03a | เมื่อ register สำเร็จ ระบบต้อง **login ให้ผู้ใช้อัตโนมัติ** และพาไปหน้าสถานะ (ฟอร์มกรอกทรัพย์สิน) ทันที ไม่ต้องกลับไปหน้า login | ✅ |
| AUTH-04 | username ต้องไม่ซ้ำกันทั้งระบบ (ทั้ง admin และผู้ใช้) **โดยไม่สนตัวพิมพ์ใหญ่/เล็ก** (เก็บเป็นตัวพิมพ์เล็ก) ใช้ได้เฉพาะ a-z 0-9 และ `_` ยาว 4–30 ตัวอักษร | ⚠️ |
| AUTH-05 | email ของผู้ใช้ต้องมีรูปแบบถูกต้อง ยาวไม่เกิน 254 ตัวอักษร และไม่ซ้ำ **โดยไม่สนตัวพิมพ์ใหญ่/เล็ก** (ยังไม่ต้องยืนยัน email ใน M1) | ⚠️ |
| AUTH-06 | password ต้องยาว 8–72 ตัวอักษร (72 เป็นขีดจำกัดของ bcrypt) และช่อง "ยืนยัน password" ต้องตรงกัน | ⚠️ |
| AUTH-07 | admin ต้องสร้างบัญชี admin อื่นได้ | ✅ |
| AUTH-08 | admin มี **ระดับสิทธิ์เดียว** (ทุกคนทำได้ทุก module) | ✅ |
| AUTH-09 | admin คนแรกต้องสร้างจาก seed ไม่มีหน้า register ของ admin | ⚠️ |
| AUTH-10 | บัญชีผู้ใช้ไม่สามารถเข้าหน้า admin ได้ และกลับกัน | ⚠️ |
| AUTH-11 | ระบบต้องมี logout | ⚠️ |
| AUTH-12 | admin ต้องรีเซ็ตรหัสผ่านของ **ผู้ใช้และของ admin คนอื่น** ได้ โดยตั้งรหัสผ่านชั่วคราวให้ (ไม่ใช้ email) ทดแทน "ลืมรหัสผ่าน" ซึ่งอยู่ M2 | ✅ |
| AUTH-13 | บัญชีที่ถูกรีเซ็ตรหัสผ่าน ต้องถูกบังคับให้ **เปลี่ยนรหัสผ่านใหม่** ก่อนทำอย่างอื่นเมื่อ login ครั้งถัดไป (รหัสผ่านใหม่ต้องไม่ซ้ำรหัสชั่วคราว และผ่านกฎ `AUTH-06`) | ✅ |
| AUTH-14 | admin รีเซ็ตรหัสผ่านของตัวเองไม่ได้ผ่านฟังก์ชันรีเซ็ต (เปลี่ยนรหัสผ่านตัวเองต้องใช้รหัสเดิม) และการรีเซ็ตทุกครั้งต้องบันทึกว่า admin คนไหนทำ เมื่อไหร่ | ⚠️ |
| AUTH-15 | fullname ต้องกรอก ยาวไม่เกิน 100 ตัวอักษร (รองรับภาษาไทย) | ⚠️ |
| AUTH-16 | session ต้องหมดอายุตามค่ามาตรฐานของระบบ และ logout แล้วใช้ session เดิมอีกไม่ได้ | ⚠️ |
| AUTH-17 | **ความเสี่ยงที่ยอมรับใน M1:** เนื่องจากยังไม่ยืนยัน email (OOS-03) ผู้ใช้สามารถสมัครด้วย email ที่ไม่ใช่ของตนได้ จึงห้ามใช้ email เป็นหลักฐานยืนยันตัวตน | ✅ (ยอมรับ) |
| AUTH-18 | ผู้ใช้สถานะ "ผ่าน" และ admin ต้องมีหน้า **โปรไฟล์ของตนเอง** แสดง fullname, username, email (แก้ username ไม่ได้) และหน้า **เปลี่ยนรหัสผ่านทั่วไป** ที่ต้องกรอกรหัสผ่านเดิม + รหัสใหม่ + ยืนยัน (ผ่านกฎ `AUTH-06`) เมื่อเปลี่ยนสำเร็จ session อื่นของบัญชีนั้นต้องหมดผล | ⚠️ |
| AUTH-19 | หน้า register ต้องมีช่องยินยอม **เงื่อนไขการใช้งานและนโยบายความเป็นส่วนตัว (PDPA)** ต้องติ๊กก่อนจึงสมัครได้ และระบบบันทึกเวลาที่ยินยอม | ⚠️ |

**เกณฑ์ตรวจรับ:** register ได้เมื่อข้อมูลครบและถูกต้อง · username/email ซ้ำ (รวมกรณีต่างกันแค่ตัวพิมพ์ใหญ่เล็ก เช่น `Somchai` กับ `somchai`) แจ้ง error ใต้ช่อง · password สั้นกว่า 8 หรือยาวกว่า 72 หรือช่องยืนยันไม่ตรงถูกปฏิเสธ · ผู้ใช้เปิด `/admin` ไม่ได้ · login ผิดแจ้งข้อความโดยไม่บอกว่า username หรือ password ผิดข้อใด

## QUAL — การตรวจสอบคุณสมบัติ

| รหัส | Requirement | สถานะ |
|---|---|---|
| QUAL-01 | หลัง register สำเร็จ ผู้ใช้ต้องมีสถานะ **"รอกรอกทรัพย์สิน"** (ผู้ใช้สถานะ "รอกรอกทรัพย์สิน" และ "รอ admin ตรวจ" เรียกรวมว่า "รอการตรวจสอบคุณสมบัติ" ในภาษาธุรกิจ แต่ในระบบเป็นคนละค่า) | ✅ |
| QUAL-02 | ผู้ใช้ต้องกรอก **ทรัพย์สินที่ครอบครอง** เป็นรายการ แต่ละรายการมี ชื่อ และ มูลค่า (ตัวเลข บาท) อย่างน้อย 1 รายการ โดยระบบต้องแสดงฟอร์มนี้ **ทุกครั้งที่ login จนกว่าจะส่งทรัพย์สินสำเร็จ** (สถานะ "รอกรอกทรัพย์สิน") | ✅ |
| QUAL-03 | ไม่ต้องแนบเอกสารประกอบทรัพย์สิน | ✅ |
| QUAL-03a | กฎของรายการทรัพย์สิน: ชื่อรายการต้องกรอก ยาวไม่เกิน 100 ตัวอักษร · มูลค่าต้อง **มากกว่า 0** ทศนิยมไม่เกิน 2 ตำแหน่ง และไม่เกิน 1,000,000,000,000 บาทต่อรายการ · มีได้ไม่เกิน **20 รายการ** ต่อรอบที่ส่ง | ⚠️ |
| QUAL-04 | เมื่อผู้ใช้กด submit ทรัพย์สิน (จากสถานะ "รอกรอกทรัพย์สิน" หรือ "ไม่ผ่าน") สถานะต้องเปลี่ยนเป็น **"รอ admin ตรวจ"** | ✅ |
| QUAL-05 | ผู้ใช้ที่ยังไม่ผ่านการตรวจ (สถานะ รอกรอกทรัพย์สิน / รอ admin ตรวจ / ไม่ผ่าน) ต้องทำได้ **เฉพาะ 4 อย่างนี้** นอกนั้นห้ามทั้งหมด: (1) ดูหน้าสถานะของตนเอง (2) ส่งหรือแก้ทรัพย์สิน — เฉพาะสถานะ "รอกรอกทรัพย์สิน" และ "ไม่ผ่าน" (3) ออกจากระบบ (4) เปลี่ยนรหัสผ่านที่ถูกบังคับตาม `AUTH-13` (ใช้ได้เฉพาะเมื่อบัญชีถูกรีเซ็ต ไม่ใช่หน้าเปลี่ยนรหัสผ่านทั่วไป) | ✅ |
| QUAL-06 | หน้าสถานะต้องแสดงตามสถานะ: รอกรอกทรัพย์สิน → ฟอร์มกรอกทรัพย์สิน · รอ admin ตรวจ → ข้อความ "อยู่ระหว่างการตรวจสอบคุณสมบัติ" · ไม่ผ่าน → เหตุผลและฟอร์มแก้ไข | ✅ / ⚠️ (ส่วนไม่ผ่าน) |
| QUAL-07 | admin ต้องดูรายการผู้ใช้ที่อยู่สถานะ "รอ admin ตรวจ" ดูรายการทรัพย์สินของแต่ละคน และกด **ผ่าน / ไม่ผ่าน** ได้ (ผู้ใช้สถานะ "รอกรอกทรัพย์สิน" ไม่ปรากฏในคิวตรวจ) | ✅ |
| QUAL-08 | เมื่อ admin ไม่ผ่าน ต้องระบุเหตุผล และผู้ใช้ต้องเห็นเหตุผลนั้น | ⚠️ |
| QUAL-09 | ผู้ใช้สถานะ "ไม่ผ่าน" ต้องแก้ทรัพย์สินและส่งตรวจใหม่ได้ เมื่อส่งแล้วกลับเป็น "รอ admin ตรวจ" | ⚠️ |
| QUAL-10 | เมื่อสถานะเป็น "ผ่าน" ผู้ใช้ต้องเข้าหน้าแรกและใช้งานเต็มรูปแบบได้ | ✅ |
| QUAL-11 | **มูลค่าทรัพย์สินรวม** (ผลรวมทุกรายการของรอบที่ผ่านตาม `QUAL-16`) คือเพดานของราคาที่ยื่นได้ (ดู BID-04) | ✅ |
| QUAL-12 | หลังผ่านแล้ว การแก้ไขทรัพย์สินต้องไม่ทำได้ใน M1 (กันการแก้เพื่อเพิ่มเพดานหลังตรวจ) | ⚠️ |
| QUAL-13 | ทุกครั้งที่ผู้ใช้ submit ทรัพย์สิน ระบบต้องบันทึกเป็น **ชุดส่งตรวจ (submission) แยกรอบ** ประกอบด้วย รายการทรัพย์สินของรอบนั้น, เวลาที่ส่ง, ผลตรวจ (รอ/ผ่าน/ไม่ผ่าน), เหตุผลถ้าไม่ผ่าน, admin ที่ตรวจ, เวลาที่ตรวจ — รอบเก่า **ไม่ถูกแก้หรือลบ** | ✅ |
| QUAL-14 | admin ต้องดูประวัติการส่งตรวจ **ทุกรอบ** ของผู้ใช้แต่ละคนได้ (รอบล่าสุดแสดงเด่นสุด) | ✅ |
| QUAL-15 | การส่งใหม่หลัง "ไม่ผ่าน" ต้องสร้างรอบใหม่ โดยฟอร์มเริ่มต้นด้วยรายการของรอบก่อนให้แก้ต่อ (ไม่ต้องกรอกใหม่ทั้งหมด) | ⚠️ |
| QUAL-16 | เพดานราคาที่ยื่นได้ (`QUAL-11`) คำนวณจากรายการทรัพย์สินของ **รอบที่ได้ผล "ผ่าน"** เท่านั้น ไม่นับรอบที่ไม่ผ่านหรือรอตรวจ | ✅ |

**เกณฑ์ตรวจรับ:** ผู้ใช้ที่ยังไม่ผ่านเปิด URL ฝั่งผู้ใช้ใดก็ตามที่ไม่อยู่ในรายการอนุญาตของ `QUAL-05` (หน้าแรก, สินค้า, ห้อง, ผลประมูล, request ยื่นราคา, โปรไฟล์ และหน้าเปลี่ยนรหัสผ่านทั่วไปเมื่อบัญชีไม่ได้ถูกรีเซ็ต) ถูกส่งกลับหน้าสถานะทั้งหมด · ผู้ใช้สถานะ "รอ admin ตรวจ" ส่งหรือแก้ทรัพย์สินไม่ได้ (request ถูกปฏิเสธ) · วิธีทำใน implementation: ใช้ allowlist ใน `before_action` กลาง (ปฏิเสธโดยค่าเริ่มต้น) ไม่ใช่ blocklist ทีละหน้า · ทรัพย์สินที่ผิดกฎ `QUAL-03a` (มูลค่า ≤ 0, ไม่ใช่ตัวเลข, ทศนิยมเกิน 2 ตำแหน่ง, เกิน 20 รายการ) ถูกปฏิเสธพร้อมข้อความใต้ช่อง

## SUSP — ระงับบัญชีผู้ใช้

การระงับเป็นเงื่อนไขแยกจาก 4 สถานะคุณสมบัติ (ผู้ใช้สถานะ "ผ่าน" ถูกระงับได้ และสถานะคุณสมบัติเดิมไม่เปลี่ยน)

| รหัส | Requirement | สถานะ |
|---|---|---|
| SUSP-01 | admin ต้อง **ระงับบัญชีผู้ใช้** ได้ พร้อมระบุเหตุผล (บังคับกรอก) และต้องมีขั้นยืนยันก่อนทำ | ✅ |
| SUSP-02 | ผู้ใช้ที่ถูกระงับต้อง login ไม่ได้ (แสดงข้อความว่าบัญชีถูกระงับ ติดต่อผู้ดูแล) และ session ที่ login อยู่ต้องหมดผลทันที | ✅ (login ไม่ได้) / ⚠️ (หมด session ทันที) |
| SUSP-03 | ผู้ใช้ที่ถูกระงับต้องยื่นราคาไม่ได้ (รวมถึง request ที่ส่งตรงเข้ามา) | ✅ |
| SUSP-04 | ~~ราคาที่ผู้ใช้ยื่นไว้แล้วในประมูลที่ยังไม่ปิดรับราคา เมื่อถูกระงับ ต้องถูกตัดออกจากการคัดผู้ชนะ~~ **แก้ไข:** ราคาที่ยื่นไว้แล้ว **ไม่ถูกตัดสิทธิ์** แม้ระงับระหว่างช่วงเปิดรับราคา (กัน admin ที่เห็นราคาสด ตาม EVT-09 ระงับผู้ยื่นสูงสุดเพื่อเปลี่ยนผู้ชนะ) การระงับมีผลเฉพาะ: ยื่นราคาใหม่ไม่ได้ทันที (SUSP-03) และยกเลิกการเข้าร่วมใน lot ที่ยังไม่เริ่ม (SUSP-06) · ถ้าผู้ถูกระงับเป็นผู้ชนะ ผลคงเดิมและ admin จัดการนอกระบบเหมือน SUSP-05 (ดู BID-17) | ⚠️ (แก้จาก ✅ เดิม รอเจ้าของโปรเจคยืนยันใหม่) |
| SUSP-05 | การประมูลที่ **สรุปผลแล้ว** ก่อนถูกระงับ ต้องไม่ถูกคำนวณใหม่ (ผลที่ประกาศแล้วคงเดิมใน M1) | ⚠️ |
| SUSP-06 | การเข้าร่วมประมูลของผู้ใช้ที่ถูกระงับในประมูลที่ยังไม่จบ ต้องถูกยกเลิก และคืนที่นั่งให้ห้อง (จำนวนผู้เข้าร่วมลดลง) | ⚠️ |
| SUSP-07 | admin ต้อง **ยกเลิกการระงับ** ได้ ผู้ใช้กลับมา login ได้ด้วยสถานะคุณสมบัติเดิม (ราคาที่ถูกตัดสิทธิ์ไปแล้วในประมูลที่จบ/ปิดรับราคาแล้วไม่ย้อนกลับ) | ⚠️ |
| SUSP-08 | ทุกครั้งที่ระงับ/ยกเลิกระงับ ต้องบันทึก admin ผู้ทำ เวลา และเหตุผล เก็บเป็นประวัติ ไม่ลบ | ⚠️ |
| SUSP-09 | การระงับ (SUSP-*) ใช้กับบัญชีผู้ใช้ (bidder) เท่านั้น บัญชี admin ใช้การปิดใช้งานตาม `ADM-05`–`ADM-08` | ⚠️ |

**เกณฑ์ตรวจรับ:** ระงับผู้ใช้ที่ยื่นราคาสูงสุดไว้ระหว่างช่วงเปิดรับราคา → ผู้ใช้นั้นยังเป็นผู้ชนะ (ราคาไม่ถูกตัด) แต่ยื่นราคาใหม่ใน lot อื่นไม่ได้ · หน้า admin แสดงป้าย "บัญชีถูกระงับ" ข้างราคานั้น · ผู้ถูกระงับ login ไม่ได้ และยิง request ยื่นราคาตรงๆ ด้วย session เก่าถูกปฏิเสธ · ประมูลที่สรุปผลไปแล้วไม่เปลี่ยนผลเมื่อภายหลังระงับผู้ชนะ

## ADM — จัดการบัญชีผู้ใช้และ admin

| รหัส | Requirement | สถานะ |
|---|---|---|
| ADM-01 | admin ต้องดู **รายชื่อผู้ใช้ทั้งหมด** (ไม่ใช่เฉพาะคิวรอตรวจ) ค้นหาด้วย username / fullname / email กรองตามสถานะคุณสมบัติและสถานะระงับ และแบ่งหน้า | ⚠️ |
| ADM-02 | admin ต้องเปิด **หน้ารายละเอียดผู้ใช้** ได้: ข้อมูลบัญชี, สถานะคุณสมบัติ, ประวัติการส่งตรวจทุกรอบ (QUAL-14), เพดานราคาปัจจุบัน, การเข้าร่วมและราคาที่ยื่นทั้งหมด, ประวัติระงับ (SUSP-08) และปุ่ม รีเซ็ตรหัสผ่าน (AUTH-12) / ระงับ / ยกเลิกระงับ | ⚠️ |
| ADM-03 | admin ต้องดู **รายชื่อ admin ทั้งหมด** พร้อมสถานะ ใช้งาน / ปิดใช้งาน | ⚠️ |
| ADM-04 | บัญชี admin มีเฉพาะ username และ password (ไม่มี fullname/email ใน M1) | ⚠️ (ค่าตั้งต้น O-9) |
| ADM-05 | admin ต้อง **ปิดใช้งาน** บัญชี admin คนอื่นได้ พร้อมเหตุผล (บังคับ) และขั้นยืนยัน และเปิดใช้งานกลับได้ | ⚠️ (ค่าตั้งต้น O-9) |
| ADM-06 | บัญชี admin **ลบไม่ได้** (เพื่อให้ประวัติการกระทำตาม `NFR-17` อ้างถึงได้เสมอ) | ⚠️ (ค่าตั้งต้น O-9) |
| ADM-07 | admin ปิดใช้งานบัญชีตัวเองไม่ได้ และระบบต้องปฏิเสธการปิดใช้งานที่จะทำให้เหลือ admin ที่ใช้งานได้ **น้อยกว่า 1 คน** | ⚠️ (ค่าตั้งต้น O-9) |
| ADM-08 | admin ที่ถูกปิดใช้งานต้อง login ไม่ได้ และ session ที่ใช้อยู่ต้องหมดผลทันที | ⚠️ |

**เกณฑ์ตรวจรับ:** ค้นหาผู้ใช้ด้วยบางส่วนของ username เจอ · กรอง "ถูกระงับ" แสดงเฉพาะผู้ถูกระงับ · admin ปิดตัวเองไม่ได้ · ปิด admin คนสุดท้ายที่ใช้งานได้ไม่ได้ · admin ที่ถูกปิดยิง request ด้วย session เก่าถูกปฏิเสธ · ไม่มีปุ่ม/route ลบบัญชี admin

## สถานะผู้ใช้ (4 สถานะ — ยืนยันแล้ว)

| สถานะ | ความหมาย | ผู้ใช้เห็น | ไปสถานะถัดไปเมื่อ |
|---|---|---|---|
| **รอกรอกทรัพย์สิน** | register แล้ว ยังไม่ส่งทรัพย์สิน | ฟอร์มกรอกทรัพย์สิน | ผู้ใช้ submit → รอ admin ตรวจ |
| **รอ admin ตรวจ** | ส่งทรัพย์สินแล้ว | "อยู่ระหว่างการตรวจสอบคุณสมบัติ" | admin กดผ่าน → ผ่าน · กดไม่ผ่าน → ไม่ผ่าน |
| **ผ่าน** | admin ตรวจแล้วผ่าน | ใช้งานได้เต็มรูปแบบ | — |
| **ไม่ผ่าน** | admin ตรวจแล้วไม่ผ่าน | เหตุผล + ฟอร์มแก้ไข | ผู้ใช้ submit ใหม่ → รอ admin ตรวจ |

ค่าในระบบ (ใช้ตรงกันทุกที่): `awaiting_assets` · `awaiting_review` · `approved` · `rejected`
