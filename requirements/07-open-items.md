# 07 ข้อที่ยังรอตัดสินใจ

ข้อที่มีผลต่อการออกแบบ ควรตอบก่อนเริ่มส่วนที่เกี่ยวข้อง ข้อที่ไม่มีคำตอบจะใช้ "ค่าตั้งต้น" ที่ระบุ

| # | คำถาม | ค่าตั้งต้น | กระทบ |
|---|---|---|---|
| O-1 | **เวลาสิ้นสุดของ event** คืออะไร: เวลาปิดห้อง (ปิดรับราคาตายตัว 30 วินาทีหลังเริ่ม) หรือเวลาปิดรับราคาจริง และสินค้าหลายชิ้นใน event เริ่ม/ปิดพร้อมกันหรือทยอยทีละชิ้น | ปิดห้อง · ทุกชิ้นเริ่ม/ปิดพร้อมกัน | EVT-05/06, BID-16, ตาราง events/lots |
| O-2 | อัปโหลดรูป: ชนิด/ขนาด/จำนวนสูงสุด | JPG/PNG/WebP, 5 MB, 10 รูป | ITEM-08 |
| O-3 | เป้าหมายผู้ใช้พร้อมกัน: สูงสุดกี่คนยื่นราคาพร้อมกันในช่วง 30 วินาที | ไม่กำหนด (ออกแบบให้ถูกต้องก่อน แล้ววัดภายหลัง) | NFR-16, การเลือก database (ปัจจุบัน SQLite) |
| O-4 | ฐานข้อมูล production: SQLite พอสำหรับการยื่นราคาพร้อมกันหรือไม่ หรือควรใช้ PostgreSQL | SQLite ตามที่โปรเจคตั้งไว้ ทบทวนหลังทดสอบโหลด | NFR-05, NFR-16 |
| O-5 | ผู้ใช้ยกเลิกการเข้าร่วมประมูลได้ก่อนเริ่มหรือไม่ | ได้ | USR-06 |
| O-6 | ผู้ใช้ที่ผ่านตรวจแล้วแก้ทรัพย์สินได้หรือไม่ (มีผลต่อเพดานราคา) | แก้ไม่ได้ใน M1 | QUAL-12 |
| O-7 | วงเงินนับแบบสะสมข้ามสินค้า หรือต่อครั้ง | ต่อครั้ง | BID-04 |
| O-8 | ผู้ใช้เข้าร่วมประมูลเพิ่มในห้องหลังเริ่มแล้วได้หรือไม่ (เหลือเวลารับราคาน้อยกว่า 30 วินาที) | ได้ จนกว่าปิดรับราคา | USR-10 |
| O-9 | จัดการบัญชี admin: ปิดใช้งาน/ลบได้ไหม, กันลบ admin คนสุดท้าย, admin มี fullname/email หรือไม่ | ปิดใช้งานได้ ลบไม่ได้ กัน admin คนสุดท้าย มีเฉพาะ username/password | AUTH-07, SUSP-09 |
| O-10 | **Design "Tier Auction UI" ขัดกับ requirement M1** หลายจุด (ดูตารางด้านล่าง) design เป็นภาพระยะยาว หรือจะเปลี่ยนแนว M1 ตาม design | ยึด requirement M1 · design เป็นภาพระยะยาว | BID, QUAL, AUTH, USR, ROOM, EVT, O-4 |
| O-11 | สินค้าต้องมีหมวดหมู่หรือไม่ ใช้ชุดไหน (design: นาฬิกา, เครื่องประดับ, ของสะสม, ยานพาหนะ) | ไม่มีใน M1 | ITEM-12, USR-01, OOS-21 |

### O-10 รายละเอียด: จุดที่ design ขัดกับ requirement

| เรื่อง | Design | Requirement M1 |
|---|---|---|
| รูปแบบประมูล | ประมูลแบบเปิด เห็นราคาปัจจุบันและประวัติ bid, bid ซ้ำได้, ขั้นต่ำการเพิ่ม, bid อัตโนมัติ (proxy), ปิดตามเวลาที่ตั้ง (ชั่วโมง/วัน) | first-price sealed ยื่นครั้งเดียวใน 30 วินาที (BID-01, BID-02) |
| Reserve | ไม่มี reserve | มี reserve (ITEM-05, BID-08) |
| ผู้ลงสินค้า | ผู้ขายลงเอง admin อนุมัติ | admin เพิ่มเอง (ITEM-01) |
| ตรวจคุณสมบัติ | KYC (บัตร + ใบหน้า + NDID + statement) → เทียร์และวงเงิน ต่ออายุ 90 วัน | กรอกรายการทรัพย์สินเอง ไม่แนบเอกสาร เพดาน = ผลรวมของรอบที่ผ่าน (QUAL-02, QUAL-03, QUAL-11, QUAL-16) |
| ระหว่างรอตรวจ | ดูสินค้าได้ | ทำได้เฉพาะหน้าที่อนุญาต ไม่เห็นสินค้า (QUAL-05) |
| การเห็นราคา | ทุกคนเห็นราคาปัจจุบันและประวัติ bid (ไม่เปิดชื่อ) | เห็นเฉพาะราคาตัวเอง หน้าแรกแสดงราคาเริ่มต้น (USR-02, USR-13) |
| Login / Register | อีเมลหรือเบอร์ + OTP + Keycloak SSO, สมัครด้วยชื่อ-นามสกุล-เบอร์ เลือก role ผู้ซื้อ/ผู้ขาย, มีลืมรหัสผ่านทาง email | username + password แยกหน้า admin/ผู้ใช้, admin รีเซ็ตรหัสให้ (AUTH-01 ถึง AUTH-03, AUTH-12) |
| ความยาวรหัสผ่าน | อย่างน้อย 12 ตัว | 8–72 ตัว (AUTH-06) |
| ห้องและ event | ไม่มีห้อง/event ไม่มีขั้นเข้าร่วม แต่ละล็อตมีเวลาของตัวเอง | มีห้อง, event และต้องเข้าร่วมก่อน (ROOM, EVT, USR-05 ถึง USR-10) |
| Tech stack | Go + PostgreSQL + Redis + Keycloak (ผัง API) | Rails + SQLite (ดู O-4) |

หน้าที่ M1 ต้องใช้แต่ design ยังไม่มี: admin จัดการวิธีประมูล/ห้อง/event/บัญชี admin · admin รีเซ็ตรหัสผ่าน · หน้าเข้าร่วมประมูล · ห้องประมูลนับถอยหลัง 30 วินาที · หน้าผลการประมูล (ชนะ/ไม่ชนะ/ไม่ขาย) · ฟอร์มกรอกทรัพย์สินเอง

**ยืนยันแล้ว (ไม่ต้องถามอีก):** เสนอราคาครั้งเดียว · 30 วินาทีหลังเริ่ม · reserve กำหนดตอนเพิ่มสินค้า · เฉพาะ admin เห็นราคา · ราคาเท่ากันยื่นก่อนชนะ · ผู้ชนะคำนวณอัตโนมัติ · สินค้าอยู่ event เดียว · ผู้ใช้ที่ยังไม่ผ่านตรวจทำอะไรไม่ได้เลย (ทำได้เฉพาะ 4 อย่างตาม QUAL-05) · เก็บประวัติทุกรอบการส่งทรัพย์สิน · admin รีเซ็ตรหัสผ่านใน M1 · ระงับบัญชีได้และตัดราคาของผู้ถูกระงับออกจากการคัดผู้ชนะ · ชำระเงิน/ส่งมอบไป M2
